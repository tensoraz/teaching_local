Section 1

Problems and problem instances

A computational problem describes a set of possible inputs and the output each input must produce. A problem instance is that problem with one particular input filled in. Think of the problem as a blank form and an instance as one filled-in copy.
Problem (general)Instance (specific input)Solution of the instance
Given n marks, find the largest72, 85, 6485
Given a whole number n ≥ 2, is it prime?n = 91No (91 = 7 × 13)
Convert a temperature from °C to °F37 °C98.6 °F
Sort a list of names alphabeticallyRavi, Anu, MeeraAnu, Meera, Ravi

A problem has infinitely many instances. When you write a program you are solving the problem, so the program must give the right answer for every valid instance, including the strange ones you did not think of while typing.

Generalization: solve the family, not one member

Young Carl Friedrich Gauss was asked to add 1 to 100. Instead of adding one by one, he paired the numbers:

Do the maths (1 + 100) + (2 + 99) + … + (50 + 51) = 50 pairs, each worth 101 = 5050.
Now generalize: for 1 to n there are n/2 pairs, each worth (n + 1), so 1 + 2 + … + n = n(n + 1) / 2.
One level higher, an arithmetic progression a, a + d, a + 2d, … with n terms has S = n/2 × [2a + (n − 1)d]. With a = 1, d = 1 you get Gauss’s formula back: a special case of the general one.

Generalizing makes one solution reusable for many inputs. But the general solution must also survive the special cases, the inputs at the edges:

Smallest input

n = 1 → 1 × 2 / 2 = 1 ✔. A list with one mark: that mark is the largest.

Empty input

n = 0 → 0. But the average of zero marks is 0 / 0: undefined! Must be handled.

Ties and repeats

Marks 90, 90, 12: two toppers. Does the spec say what to print?

Classifying problems by difficulty

Well-defined vs ill-defined

“Sort these 60 marks” has clear input, output and rules. “Make the canteen better” does not. An ill-defined problem must be turned into a well-defined one (by asking questions) before a computer can help.

Solvable vs unsolvable

Some problems have no algorithm at all. Alan Turing proved (1936) that no program can look at every possible program and decide whether it will eventually stop. This is the halting problem.

Tractable vs intractable

Tractable problems are solved fast even for big inputs. Intractable ones have known solutions whose running time explodes as the input grows, so we settle for good approximate answers.

Do the maths: when “just try everything” explodes A bus must visit n colleges and come back, using the shortest route. Trying every route means checking (n − 1)! / 2 routes.
5 colleges: 4! / 2 = 12 routes · 10 colleges: 9! / 2 = 1,81,440 · 20 colleges: 19! / 2 ≈ 6 × 1016.
At a billion routes per second, 20 colleges take about 2 years. Adding one more college multiplies the work by about 20.

Section 4

Problem-solving steps: Understand, Plan, Execute, Review

The mathematician George Pólya described four steps in his book How to Solve It (1945). They work for maths homework, for programs and for most of life.

1 · Understand the problem

What is given? What is asked? What are the conditions? Can you restate it in your own words? Solve one small instance by hand.

2 · Plan (devise a solution)

Have you seen a similar problem? Break it into subproblems. Write the algorithm in steps or pseudocode.

3 · Execute (carry out the plan)

Follow the plan step by step. Translate it to C, compile, run. Check each step as you go.

4 · Review (look back)

Test with normal and special cases. Is the answer sensible? Is there a faster or simpler way? Can you reuse the method?

Worked example: the four steps on “average marks”

1

Understand

Solve a tiny instance by hand: marks 72, 85, 64 → sum 221 → 221 ÷ 3 = 73.67. Now you know what the program must print.

2

Plan: break into subproblems, then write the algorithm

Algorithm ClassAverage Input : n, then n marks Output: average to 2 decimal places Step 1: Read n. If n < 1 or n > 200, print an error and stop. Step 2: sum ← 0 Step 3: Repeat for i ← 1 to n Read m. While m is not a whole number from 0 to 100, print "Invalid" and read m again. sum ← sum + m Step 4: avg ← sum ÷ n Step 5: Print avg with 2 decimals Step 6: Stop
3

Execute: translate to C

You will learn every line of this from Unit 2. For now, notice how each line matches a step of the algorithm.

#include <stdio.h>

int main(void)
{
    int n, m, sum = 0;

    printf("How many students (1 to 200)? ");                 /* Step 1 */
    if (scanf("%d", &n) != 1 || n < 1 || n > 200) {
        printf("Error: n must be a whole number from 1 to 200.\n");
        return 1;
    }
    for (int i = 1; i <= n; i++) {                             /* Step 3 */
        printf("Marks of student %d: ", i);
        while (scanf("%d", &m) != 1 || m < 0 || m > 100) {   /* validate */
            int c;
            while ((c = getchar()) != '\n' && c != EOF)
                ;
            printf("Invalid. Enter marks from 0 to 100: ");
        }
        sum = sum + m;
    }
    printf("\nAverage = %.2f\n", (float)sum / n);              /* Steps 4, 5 */
    return 0;
}

Specification: inputs, outputs, validation, conditions

Input/output specification

A specification lists every input and output with its name, type, valid range and unit. Anyone reading it, including a compiler-happy teammate, should be able to write the same program.

NameMeaningTypeValid values
Inputnnumber of studentsinteger1 to 200
Inputm (n times)marks of one student, out of 100integer0 to 100

Input validation: never trust the input

Users mistype, press Enter too early, and sometimes try strange values on purpose. Garbage in, garbage out: a program that accepts bad input will produce a wrong answer that looks right. Validation checks input before using it.

CheckQuestion it asksExample of input it rejects
Type checkIs it the right kind of data?Marks entered as abc
Range checkIs the value inside the allowed limits?Marks = 105 or −5
Presence checkWas anything entered at all?An empty name field
Format checkDoes it follow the required pattern?Date typed as 2025/31/12 instead of DD-MM-YYYY
Length checkIs it the right number of characters?A 9-digit mobile number
Consistency checkDoes it agree with other inputs?Date of leaving earlier than date of joining
Two ways to react to bad input Reject and stop with a clear message (used for n above), or ask again in a loop until the input is valid (used for each mark). Choose the one that suits the user, and write the choice in the specification.

Pre-conditions and post-conditions

Specifications are often written as a contract between an algorithm and whoever uses it:

Pre-condition

What must be true before the algorithm runs. It is the caller’s promise. If it is broken, the algorithm promises nothing.

Post-condition

What will be true after the algorithm finishes, provided the pre-condition held. It is the algorithm’s promise.

AlgorithmPre-conditionPost-condition
ClassAverage1 ≤ n ≤ 200 and every 0 ≤ mi ≤ 100avg = (m1 + … + mn) ÷ n, and 0 ≤ avg ≤ 100
Square root of xx ≥ 0result r ≥ 0 and r × r ≈ x
Binary search for keythe list is sortedreturns i with a[i] = key, or “not found” if key is absent
Grade from marks0 ≤ marks ≤ 100exactly one of A, B, C, D, F
Validation and pre-conditions work togetherValidation code at the start of a program is what makes the pre-condition true. After the checks pass, the rest of the code may safely assume it. In grade_check.c you will see the comment /* pre-condition now holds: 0 <= marks <= 100 */ right after the checks.
Section 6

Algorithms and solution approaches

An algorithm is a finite sequence of precise, unambiguous steps that solves every instance of a problem. The word comes from the 9th-century mathematician al-Khwarizmi.

Five properties of an algorithm (Knuth)

PropertyMeaningBreaks it
FinitenessStops after a finite number of steps“Keep adding 1 to x” with no stopping rule
DefinitenessEvery step is exact and unambiguous“Add salt to taste”, “pick a big number”
InputZero or more well-defined inputs—
OutputAt least one output related to the inputSteps that compute but never report anything
EffectivenessEach step is basic enough to do with pen and paper“Find the largest prime number”

Algorithm development: stepwise refinement

Start with one rough sentence, then refine each line into more detailed steps until every step is something a computer can do directly. Standard format: a name, input, output, then numbered steps ending in Stop.

Algorithm FindMax (rough) 1. Look at all the marks 2. Remember the biggest 3. Print it
Algorithm FindMax (refined) Input: n ≥ 1, marks m[1..n] Output: max Step 1: max ← m[1] Step 2: For i ← 2 to n If m[i] > max then max ← m[i] Step 3: Print max Step 4: Stop

Solution approaches

GreedyTake the best-looking choice at each stepGiving change with the largest note firstNot always the best overall

200 → 89 left · 50 → 39 · 20 → 19 · 10 → 9 · 5 → 4 · 2 → 2 · 2 → 0, so 7 pieces, which is the minimum here.

Section 8

Correctness and testing

An algorithm is correct if, for every input that satisfies the pre-condition, it stops and the post-condition is true. That has two parts:

Partial correctness

If it stops, the answer is right.

Termination

It always stops: no infinite loop.

Total correctness

Both together.

Reasoning with a trace table and a loop invariant

After pass isumInvariant: sum = 1 + … + i
0 (start)0empty sum = 0 ✔
111 ✔
231 + 2 ✔
361 + 2 + 3 ✔
4101 + 2 + 3 + 4 = 4 × 5 / 2 ✔

A loop invariant is a statement that is true before the loop and stays true after every pass. Here: “after pass i, sum = 1 + 2 + … + i”.

When the loop ends, i = n, so sum = 1 + … + n: exactly the post-condition. And the loop ends because i grows by 1 each pass and stops at n.

Designing test cases

Testing cannot prove a program correct (“testing shows the presence, not the absence, of bugs”, Edsger Dijkstra), but well-chosen tests find most bugs. Two classic ideas, shown for the grade problem 80–100 A · 60–79 B · 50–59 C · 40–49 D · 0–39 F:

  • Equivalence classes: inputs in the same class should behave the same, so test one from each: −5, 20, 45, 55, 70, 90, 150, “abc”.
  • Boundary values: bugs hide at the edges (> written instead of >=), so test both sides of every boundary: −1, 0, 39, 40, 49, 50, 59, 60, 79, 80, 100, 101.

Section 9

The role of data structures in problem solving

A data structure is a way of organising data in memory. The structure you choose decides which algorithms are possible and how efficient they are. Niklaus Wirth summed it up in a book title: Algorithms + Data Structures = Programs (1976).

Average of 60 marks

Keep a running sum and a count. Each mark is added and forgotten. 2 variables, whatever the class size.

Median of 60 marks

The middle value can only be found if all 60 marks are stored (an array) and sorted. Memory grows with n.

TreeFolders inside foldersFile systems; a family tree
